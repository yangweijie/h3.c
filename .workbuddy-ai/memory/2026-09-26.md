## 任务：让 h3c 的 DiT 支持 mere-run 的 int4 量化权重

用户指定：`dit 支持 /Volumes/data/MODELS/h3-16gb-q4/transformer.safetensors int4 量化后的`，
选定路线：**h3c 走转换脚本**（C 代码不动，额外落一份权重）。

### 产出

- `fastvideo_qad/scripts/export_h3_q4_native.py` — 转换器（新建）
  - 读 mere-run q4（MLX affine 4-bit g64，U32 打包），反量化 → 按 ConvRot 旋转 →
    以 group=64 重新仿射量化 → 低位先打包成 U8 → 写 `{key}` /
    `{key}_scale` / `{key}_bias`（`{key}` 是**含 `.weight` 的完整键**，
    所以实际是 `blocks.0.attn.qkv_proj.weight_scale`）
  - 其余全部键（含 `blocks.N.adaln_proj.linear.*`，q4 文件里被省略）从发布版
    BF16 目录原样按字节拷贝
  - `token_refiner.*`（2 块 × 4 矩阵）默认**不量化、按字节拷贝**：它由文本编码器
    模块加载（`h3_text_encoder.c:227`）并硬要求 BF16。`--token-refiner quantize`
    可以强制量化，但引擎会拒。代价只有 0.179 GiB
  - 分片写 safetensors（自带 writer，不依赖 torch/bf16 numpy）+ index.json + config.json
  - `--verify` 会重新从磁盘按引擎的推导规则还原格式并报误差
  - `--source {q4,bf16}`：bf16 直接量化发布版（单次量化，误差更小）
- `/Volumes/data/MODELS/h3c-q4-native/` — 转换后的可加载模型目录
  - `FL2VA/transformer`：18 shards / 935 tensors / 35.93 GiB（533 s 生成）
  - 其余 `FL2VA/{tokenizer,video_vae,audio_vae}` 软链到 h3c-official

### 关键结论（都是实测，不是推断）

1. **q4 文件的字节契约**：`mx.quantize(to_slabs(发布版BF16), group_size=64, bits=4)`
   与 q4 文件的 packed/scales/biases **逐字节相同**。由此一次性确定：
   - 打包顺序 = 首个码占低位（低位先）
   - 反量化式 = `w = code*scale + bias`（不是 `(code-bias)*scale`）
   - 行序 = q4 的 qkv_proj 是**全局 slab** `[all-q; all-k; all-v]`，发布版 BF16 是
     **按 head 交错** `[h0q,h0k,h0v,h1q,...]`；mere-run 转换时做了重排
   - 旋转空间 = **未旋转**（与发布版 BF16 同空间）。q4 是从发布版 BF16 直接量化来的
     （`source_precision: released mixed BF16/F32`），mere-run 转换器里没有任何 Hadamard 代码
2. **h3c 的 packed group 格式契约上就是"ConvRot 旋转后"的空间**：
   - 流式 grouped 分支无条件调用 `h3_weight_unrotate_rows`（`h3_dit.c:1785`），
     **没有** `H3_INT8_UNROTATE` 开关（常驻路径 `h3_weights.c:853` 有，两条路不一致）
   - 所以必须旋转；旋转已量化的矩阵必然要重新量化 → 二次量化
3. **qkv 行序：转换器不做任何置换**。q4 已是 slab，而引擎也消费 slab：
   流式 grouped 分支对 STREAM_QKV 传 `layout=1`，即
   `dst = 3*(slot%heads) + slot/heads`（`h3_dit.c:1755`、`shader h3_shaders.metal:137`），
   把 slab 重排成注意力内核索引的按 head 交错行
   （内核读 `qkv[base+d]` / `qkv[base+head_dim+d]` / `qkv[base+2*head_dim+d]`）。
   注意 `h3_shaders.metal:80-85` 的注释把两个布局的**命名写反了**，代码是对的。
4. **必须 `--ssd-streaming`**：grouped 的流式机制只在 `dit->ssd_streaming` 分支里建立
   （`h3_dit.c:2822`）。常驻路径 `load_block` → `bf2_convrot` 只认 I8/BF16，读不了 U8 打包。
5. **精度代价（实测）**：
   - `--source q4`：对 BF16 的累计 relRMS **mean 0.1318 / max 0.1445**（二次量化）
   - `--source bf16`：单次量化，约 **0.091**（同尺寸输出，误差小 ~1.4×）
   - **q4 文件自身**相对发布版 BF16 就已经是 **mean 0.096 / max 0.104** —— 也就是说
     4-bit affine g64 这个格式本身在这个权重上就只有 ~9% 精度，二次量化只额外加了
     3.6 个点。想更准只能上 6-bit / 更小 group，不是转换器能解决的
   - 旋转自逆性 `max|R(R(x))-x| = 4.8e-07`（float32 舍入）
6. **体积真相**：q4 文件只有 11.33 GB 是因为它**省略了 50 个 `adaln_proj.linear.weight`**
   （每个 BF16 `[96768, 2688]` = 496 MiB，合计 24.2 GB），不是 4-bit 的功劳。
   完整可加载目录 = 34.90 GiB。h3c 逐个加载 adaln_proj 后立刻释放
   （`h3_dit_schedule.c:553`），所以 26 GB AdaLN 在 16 GB 机器上能流式跑。
7. 本地**没有** ConvRot INT8 发布版（`h3c-official/FL2VA/transformer` 只有 BF16/F32，
   没有 `_scale` 键），所以 `export_h3_int6_native.py --base <ConvRot dir>` 这条现成路
   在这里跑不了；它的注释假设 base 是旋转过的。

### 踩过的坑（两次都花了整轮排查）

**坑 1：辅助张量命名多写了一个 `weight`。**
第一版转换器写的是 `{key}_weight_scale`（把 `_weight_scale` 接到已含 `.weight`
的键上 → `...qkv_proj.weight_weight_scale`）。`h3_weight_grouped_spec`
（`h3_weights.c:623-628`）用 `name + "_scale"` 精确查表，所以：
- 返回 **0**（不是 -1），于是 `prepare_stream_source`（`h3_dit.c:1217`）报
  `grouped streaming weight schema mismatch`
- **`--info` 查不出来**（它只数张量个数），必须真跑一次生成
- 返回 0 的三条路径（weight 非 U8 / 缺 `_scale` / 缺 `_bias`）共用同一条外层错误，
  所以从错误信息看不出是命名问题
现已加 `scale_key()` / `bias_key()` 两个 helper + `assert` 回归守卫。

**坑 2：流式失败的真实原因被吞掉，伪装成 `unknown Metal error`。**
`read_stream_layer` 的非流水线分支（`h3_dit.c:1906`，即默认
`H3_DIT_STREAM_WORKERS` 未设时的路径）：
```c
if (!stream_fill_slot(worker, position) ||
    !stream_consume_slot(worker, position)) { worker->job.ok = 0; break; }
```
`stream_fill_slot` 把消息写在 `ring->error[index]`，只有 `stream_consume_slot`
会把它拷进 `job->error`；`||` 短路后 `stream_consume_slot` 根本不会被调用。
于是 `job->error` 为空，`h3_dit.c:2110` 退回
`h3_gpu_error(dit->gpu)` → `"unknown Metal error"`。
**排查技巧**：设 `H3_DIT_STREAM_PIPELINE=1` 强制走读线程，真实错误就会显出来。

### 运行内存（16 GiB 机器上是硬约束）

- 自适应常驻预算（`h3_dit.c:2756-2790`）：`resident = (available - activation_reserve) / 0.5 GiB`，
  `activation_reserve = 1 GiB + 视频/音频 latent`。它会**几乎吃满**可用内存：
  实测自动挑 10~13 块，然后在 denoise 第 0 块就被 macOS **SIGKILL（exit 137）**。
- 关键：**这跟 4-bit 无关**。BF16 发布版用同样的自动预算也会被 SIGKILL。
- **可用解法：`H3_DIT_RESIDENT_BLOCKS=4`**。实测两个模型都稳定跑完
  （BF16 144 s / 4-bit 102 s；4-bit 反而更快，因为只读 36 GB 而不是 62 GB）。
- 常驻块数**不影响数值**：13 块与 4 块的 BF16 输出 latent 与 mp4 **md5 完全相同**，
  印证了 `h3_dit.c:2846` 那段"常驻块走同一条流式路径"的注释。
- grouped 源的第二个内存放大点：`workers == 1`（默认）时
  `chunk_rows = source->rows`（整矩阵）+ `fast = 0`（主机 staging），
  于是 fc1 一次要 `28672*5376*4` = 616 MB 的 f32 scratch **加上** 308 MB bf16 staging。
  `H3_DIT_STREAM_WORKERS=4` 会把 `fast` 置 1（直接写 slot）并把 chunk 降到 1024 行，
  峰值降到 ~22 MB。

### 逐位校验：文件 → 引擎（决定性证据）
结论：**转换是逐位正确的**，视频差异纯粹来自 4-bit 权重误差本身。

方法：`H3_DEBUG_CONVROT=1` 会让引擎把自己**去旋转后写进 slot 的 BF16 权重**
打印出来（`h3_dit.c:1806-1838`），这是引擎对文件的最终解读。把它和
"用 Python 按同一套规则复算我们的文件"对比：

| 探针 | 位置 | max&#124;Δ&#124; | bf16 ULP |
|---|---|---|---|
| `out_proj[0][0..7]` | layout=0，slot 行 0 | **0.00035** | 0.00049 |
| qkv element 7168 | layout=1 后 slot 行 1 列 1792 | **0.00074** | 0.00098 |
| qkv element 14336 | layout=1 后 slot 行 2 列 3584 | **0.00041** | 0.00098 |

全部在 1 个 bf16 ULP 之内 → 一次性证明：低位先打包、`w=code*scale+bias`、
group=64 的 scale 形状、`_scale`/`_bias` 命名、**ConvRot 旋转与引擎去旋转一致**、
以及 qkv 的 slab→按 head 交错 置换全部正确。

复算方式（Python 侧）：
```python
w = dequantize_grouped(unpack_low_nibble_first(packed), scale, bias)
w = rotate_rows(w)            # 引擎会再做一次 R，R(R(W))=W
# out_proj: 无行置换；qkv: 先按 dst=(3*(s%56)+s//56)*128+dim 复现置换，
#          再按 **元素偏移** 取数（不是行偏移，见下）
```

**顺带发现的第 3 个小缺陷（仅影响调试输出）**：
qkv 探针写的是 `uint32_t rows[3] = {0, 7168u, 14336u}` 并当成行号打印
`q[0]/k[0]/v[0]`，但 `h3_gpu_tensor_read_bf16_range`
（`h3_gpu.m:913`）的第二个参数是**元素偏移**，不是行偏移。
于是它实际读到的是"交错布局 slot 的行 1 列 1792"和"行 2 列 3584"，
标签完全对不上（q[0] 恰好对是因为元素 0 就是行 0）。
排查时差点被它误导成"qkv 行序错了"。真要按行探，应传
`{0, 56*128*5376, 112*128*5376}`（或改用按行的读取接口）。

### 体积账：为什么 q4 是 10.56 GiB 而产物是 35.93 GiB

实测（按 dtype × key 前缀分类求和，不是估算）：

| 类别 | q4 文件 | 我们的产物 | 差 |
|---|---|---|---|
| AdaLN 投影 | **0** | 24.28 GiB | **+24.28** |
| 4-bit 量化矩阵 | 10.15 GiB | 10.21 GiB | +0.06 |
| token_refiner | 0.40 GiB (4-bit) | 1.44 GiB (BF16) | +1.03 |
| 顶层（embeds/norms） | ~0 | ~0 | 0 |
| **合计** | **10.55 GiB** | **35.93 GiB** | **+25.38** |

q4 文件本体 11,333,407,848 B = 10.56 GiB，`adaln` 键数量 = **0**。
发布版有 **51** 个 AdaLN 权重（50 blocks + `final_layer.adaln_proj.linear.weight`），
每个 BF16 `[96768, 2688]` = 496.1 MiB，合计 24.279 GiB。

**4-bit 那一半两边一样大**（0.5625 B/param，逐个 out_proj 对过：
q4 与我们的 codes+scale+bias 都是 21,676,032 B，逐字节相同）。

**这个差额从转换脚本里减不掉**：
- **F16 没用** —— BF16 和 F16 都是 **16 bit/param**。（我一度算错成 F16 是 1 B/param
  并据此加了 `--adaln f16`，实测产物仍 35.93 GiB，已回滚。教训：改 dtype 前先查
  `_BYTES_OF`。）
- 引擎的 AdaLN 加载器 `weight_bf16_any`（`h3_dit_schedule.c:94`）只接受
  **BF16 / F16 / F32**，所以 AdaLN 存不了 packed 4-bit，除非改 C 让它在本机反量化
  （那样 24.28 → 6.95 GiB，但 AdaLN 是给所有激活做调制的，4-bit 误差的破坏力
  比注意力/MLP 矩阵大得多，必须先测）。
- 想完全对齐 mere-run 就得在 C 里实现 AdaLN 输出缓存（`cache_covered_weights_omitted`）。

顺带确认：AdaLN 的 dtype 不参与格式探测 —— `h3_dit_schedule.c:469` 的探针只看
`ndim`/`shape[1]`，不看 dtype。

### 确定性核查：mp4 md5 不是判据

追查一个反常的 mp4 md5 差异时确认：

- 同一模型、同一参数（`--ssd-streaming --width 256 --height 256 --frames 22
  --steps 2 --seed 42`）连跑 **5 次**，`--latent-out` 的 latent **逐字节相同**
  （relRMS 0.000000，max|d|=0），解码帧 **逐像素相同**（PSNR = inf）。
- 曾有一次 mp4 的 md5 不同，但它的 latent 与其它运行**逐字节相同**，
  解码帧 PSNR = inf、尺寸也相同（87237 B）—— 差异只在 **mp4 容器字节**，
  不是数值差异。
- 常驻块数同样不影响数值：9 块与 4 块 resident 得到同一个 md5。

**结论：判断确定性要比 `--latent-out` 的 latent 或解码帧，不要比 mp4 的 md5。**
（BF16 那边也是：13 块与 4 块的 latent 与 mp4 md5 都相同。）

## 为什么 ConvRot int8 只要 22 GB（2026-09-26 14:39）

用户追问 `/Users/jay/h3_sys/MiniMax-H3-Convrot/FL2VA/transformer/fastvideo_fasth3_8step_v2_pruned_int8_convrot.safetensors`
（22,128,378,696 B = **20.61 GiB**，1098 张量）为什么比 h3c-q4-native 的 35.93 GiB 小。

### 用同一分桶口径实测四个模型（GiB）

| | AdaLN | MLP | Attention | token_refiner | 其它 | 合计 |
|---|---|---|---|---|---|---|
| h3c-official BF16 | 24.288 | 21.533 | 14.355 | 1.436 | 0.116 | **61.73** |
| 同架构 int8（推算） | 12.144 | 10.767 | 8.972 | 0.718 | 0.116 | **32.72** |
| **这个 int8 pruned（实测）** | **0.081** | 10.773 | 8.979 | 0.718 | 0.057 | **20.61** |
| h3c-q4-native 4bit | 24.288 | 6.056 | 4.037 | 1.436 | 0.116 | **35.93** |
| mere-run q4 | **0** | 6.056 | 4.037 | 0.404 | 0.057 | **10.55** |

### 结论：22 GB 的主因不是 int8，是**模型结构被剪了**

`config.json` 的 `num_layers:50 / hidden_size:5376 / ffn_hidden_size:14336 /
adaln_out_features:96768` **全部与发布版一致** —— 剪的不是层数或宽度，是**条件注入路径**：

- 发布版：`blocks.N.adaln_proj.linear.weight` BF16 `[96768, 2688]`，50 个 = **24.288 GiB**
- 这个 int8：同一个键是 **F16 `[96768, 8]`**，50 个 = **0.072 GiB** → **336× 压缩**
- 输入从 2688 维时间嵌入 MLP 换成 **`adaln_t_table` F32 `[1025, 8]`** 查表
  （`h3_dit_schedule.c:275-295` 的 `interpolate_curve_table`，线性插值）
- `final_layer.adaln_proj.linear.weight` 同样 `[10752, 2688]` → `[10752, 8]`
- 每 block AdaLN 参数 260.0M → 0.77M；50 block 合计 13.0B → 38.7M
- `time_embedder.safetensors`（4 张量 / 63 MB，全 F32）被**拆出**主权重文件

这正是文件名里 `pruned` 的含义，也是 h3c `h3_dit_schedule.c:390-500`
"table mode" 分支存在的原因 —— **h3c 早就支持这个格式**。

### 差额闭环

- 同架构 int8 = 61.559/2 + 0.171 = 30.95 GiB，再加 VSA 的 `to_gate_compress`（+1.794）= **32.72 GiB**
- 实际 **20.61 GiB** → 差 **12.11 GiB**
- 其中 AdaLN 一项：同架构 int8 会给 12.144，实际 0.081 → **省 12.06 GiB**
- 残差 0.05 GiB = `time_embedder` 移出（0.059）+ `final_layer` AdaLN 同样缩到 rank-8

### int8 逐行量化其实比 4-bit 更"贵"

`comfy_quant` 侧车内容（每个量化矩阵都有一份，U8[72]）：
```json
{"format": "int8_tensorwise", "convrot": true, "convrot_groupsize": 256}
```
- `{name}.weight` I8 `[rows, cols]`；`{name}.weight_scale` F32 `[rows, 1]` —— **逐行一个 scale，无 bias**
- ≈ **1.00074 B/参数**，对比 h3c 4-bit group-64 的 **0.5625 B/参数** → int8 **大 1.78×**
- 实测印证：MLP 10.773 / 6.056 = 1.779；Attention（去掉 `to_gate_compress` 1.794）
  7.185 / 4.037 = 1.780

**所以 int8 的 22 GB 不是"存得更巧"，而是模型本身小了 12 GiB。**

### h3c 侧的两个重要事实（顺手确认）

1. **`attn.to_gate_compress` 在全部 `.c/.h/.m` 里零引用** —— VSA（Video Sparse Attention）
   专用，h3c 不实现。所以拿这个 checkpoint 直接跑，注意力会**缺掉 VSA 门控**，语义不等价。
   （`fastvideo_qad/scripts/mlx_int8_to_h3.py:44` 的注释也这么说。）
2. **`H3_MAX_STEPS = 1000`**（`h3_host.h:14`）；`BLOCK_OUTPUT = 3*6*5376 = 96768`。

### 真正的可操作结论：AdaLN 输出缓存

`h3_dit_schedule_precompute`（`h3_dit_schedule.c:440-610`）**一次性算出所有 step 的 AdaLN 调制**
（`time_rows = count`，`prepare_rows` 里 video/audio sigma 相等则 1 行、不等则 2 行，
再加 condition 各 1 行），算完立刻 `free_tensor(&weight)` —— 24.288 GiB 的权重
**只被读一次**，产出只有 `50 × time_rows × 96768 × 2 B`：

- 每行 9,698,304 B = **9.25 MiB**（50×96768×2 + 10752×2）
- `--steps 2`（实测 `count=3`）→ **27.7 MB**
- `--steps 8` → 约 74–148 MB
- `--steps 1000` → 约 9.0–18.0 GB

**把这个调制张量落盘，h3c-q4-native 就能从 35.93 GiB 掉到约 11.7 GiB**
（= 10.55 mere-run + 1.03 token_refiner BF16），与 mere-run 的 11.33 GB 同量级。
缓存是 `(sigmas, visual_condition, audio_condition)` 的纯函数；**LoRA 除外**

## 实现 AdaLN 输出缓存：35.93 GiB → 11.78 GiB（2026-09-26 14:57）

用户说"要"，于是把上一条分析里的正路做出来了。

### 改动

**`h3_dit_schedule.c` / `.h`（+229 / +24 行）**

1. **拆分 `prepare_rows`** → `prepare_times`（纯 CPU、不碰权重、不碰 GPU，产出 `times[]`）
   + `prepare_features`（时间特征构建）。唯一调用点在 precompute，所以拆开无副作用。
   拆开的原因：缓存路径必须能**先**拿到本次的 `times[]` 去校验，再决定是否加载权重。
2. **缓存读取路径** `load_cached_adaln`：探测 `blocks.0.adaln_cache`，命中则
   逐位比对 `adaln_cache_times` 与本次 schedule，然后直接加载 50 个 block + final。
   完全不碰 51 个 `adaln_proj.linear`。缓存模式下 `lora_count > 0` 直接拒绝。
3. **导出路径** `dump_adaln_cache` + `H3_DIT_ADALN_CACHE_DUMP=<path>`：
   raw 头 `magic"H3ADALN1"` + `uint32[4] = {time_rows, blocks, block_output, final_output}`
   + `f32 times[]` + `u16 blocks[50][R*96768]` + `u16 final[R*10752]`。
   只有调制，没有权重 —— steps=8 是 138.7 MiB。
4. 缓存模式下进度回调补一次 `progress(50, 50)`，否则进度条停在 0/50。

**顺手修掉一个既有 bug**：`goto failed` 会跳过 `h3_gpu_tensor *time = ...` 的声明，
而 `failed:` 里 `h3_gpu_tensor_free(time)` 读的是**未初始化指针**。
原有 3 条 `goto failed` 就已经踩在上面，我新增的校验失败路径会让它更容易命中。
把 `time` 提到函数顶部初始化为 NULL。

**`fastvideo_qad/scripts/export_h3_adaln_cache.py`（新，~330 行）**
读 raw dump → 流式写 `adaln_cache.safetensors`（不整块进内存，1000 步时 dump 有 ~9.7 GB）；
`--trim-to` 写**新目录**并剔除 51 个 AdaLN 矩阵（源模型不动）；
`--verify` 逐字节复查；`--dry-run` 预估。同时把 `export_h3_q4_native.py` 的 docstring
里"这需要以后在 C 里实现 AdaLN 缓存"改成指向本脚本。

## 预生成 4/8/20 步缓存，支持后续自由切换

需求："预先生成 4步 8步 20步缓存 方便后续切换"。上节遗留的第 1 条就是这个，本次做掉。

### 设计：缓存按 `--steps` 分键

`H3_ADALN_CACHE_{TIMES,BLOCK,FINAL}_FORMAT` 全部带 `s%d` 步数后缀，
一个 transformer 目录里可并存任意多份，文件名 `adaln_cache_s{steps}.safetensors`。
`blocks.0.adaln_cache_s{steps}` 存在即选中缓存路径，所以切换步数就是换一个 `--steps`。
`h3_st_inventory_dir` 只按 `*.safetensors` 后缀扫目录，天然认得新缓存，无需改动。

### 关键发现：三种条件模式的行数嵌套

条件行**追加在 step 行之后**，顺序固定 visual 再 audio：

| 模式 | time_rows | 条件行 |
|---|---|---|
| text-to-video | `2*steps - 1` | 无 |
| 首/末帧 I2V | `2*steps` | visual |
| 参考图 Ref2VA | `2*steps + 1` | visual + audio |

（`2*steps - 1` 而不是 `2*steps`：第 0 步 video==audio，只占 1 行。）

因为短模式的 `times[]` 恰好是长模式的**前缀**，一份缓存能服务全部三种模式 ——
只要导出时把两个条件行都算出来。`H3_DIT_ADALN_CACHE_DUMP` 因此**同时强制
`visual_condition = audio_condition = 1`**（先前只强制了 visual）。

**修掉一个死循环陷阱**：只强制 visual 时，Ref2VA 需要 `2s+1` 行而缓存只有 `2s` 行，
会被拒绝并提示"重建缓存"—— 但重建出来的还是 `2s` 行，永远修不好。同时强制两个条件行后，
缓存是 `2s+1` 行，三种模式分别按前缀/精确命中。

（纯音频参考 `H3_LAYOUT_REF_AUDIO` 无图是唯一不覆盖的模式：它只有 1 个条件行，
会落在 visual 行的位置上而被 memcmp 拒绝。该模式 CLI/REPL 都构造不出来，只有 C API 可达。）

### 顺手补的报错

缓存专用 checkpoint 连 `blocks.0.adaln_proj.linear.weight` 都没有，所以跑一个没缓存的
步数时，原来只会报 `required weight is absent: blocks.0.adaln_proj.linear.weight`，
看不出"这个模型只是没存这一档"。新增判断 `!cache_tensor && !adaln_probe`（只在注定失败的
路径上成立），改成：

```
this checkpoint ships AdaLN caches but none for 6 steps, and it has no adaln_proj
weights to fall back on; export a cache at these steps with H3_DIT_ADALN_CACHE_DUMP
```

### 纠正一处早先的误读

上节曾写"缓存模式下 `schedule->blocks[]` 装的是调制而不是权重，所以 gate 排名会坏"。
**这是错的**：非缓存路径下 `h3_gpu_linear_bf16` 也把投影结果写进 `schedule->blocks[]`，
两条路装的都是调制；`h3_dit_schedule_gate_scores` 读的正是调制 slot 2/5。缓存逐位复现
同一内容，且 `time_rows` 取本次运行的值，所以 `!layers N` 块剪枝在缓存模式下**结果完全一致**。

### 验证：4/8/20 三档全部 bit-identical

导出 dump（预测 `32 + rows*9,698,308` 字节，三档全部**逐字节命中**）：

| 4 | 9 | 87,284,804 | 87,284,804 ✓ | 13d2bdb3… |
| 8 | 17 | 164,871,268 | 164,871,268 ✓ | 35f7a335… |
| 20 | 41 | 397,630,660 | 397,630,660 ✓ | 73867699… |

裁剪：丢 102 个 AdaLN 张量（24.29 GiB），留 11.65 GiB，装 3 个缓存 619.7 MiB，
目录 **12.25 GiB**（原 35.93）。`--verify` PASS：3 份缓存各 52 键、schedule 键逐位、
block 0/49 与 final 逐字节、残留 `adaln_proj` 0 个。

A/B（同一 prompt/256×256/22 帧/seed 42，A = 全权重 `h3c-q4-native`，B = 缓存模型）：
